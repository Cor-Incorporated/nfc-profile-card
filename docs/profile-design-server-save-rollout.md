# デザイン保存のサーバー集約（Draft）

公開プロフィールのISRを検討する際、旧タブのFirestore直接書込が失効通知を通らない問題への対応案です。この変更だけでは、FirestoreのcommitとNext.jsのキャッシュ失効が原子的にならず、公開情報の即時撤去は保証できません。

## 段階的な展開

1. ISRが無効のまま、新しいアプリを配信する。新SimpleEditorは認証済み `PUT /api/users/me/profile/design` で保存し、デザイン画面の読込失敗・別タブ競合・認証失効・保存失敗を表示する。Firestoreの既存rulesはこの段階では維持する。
2. 新アプリの保存と開発用リセットを、テストアカウントで実ブラウザ確認する。新旧のタブを同時に開き、古いタブを残したまま新アプリへ更新する。
3. Firestore rulesを配信し、本人SDKからの `profile/data` create/update/deleteを拒否する。既に開いている旧タブでは保存が失敗して汎用の「保存失敗」が表示されるため、再読込して新UIで保存するよう案内する。旧タブの保存内容は自動移行しない。
4. 新UIで成功保存・別タブ409・認証401・一時障害503・旧タブpermission-deniedを再確認する。ページを再読込して値が残ること、公開プロフィールも更新されることを実データで確かめる。
5. 東京リージョン配置後の本番TTFBと許容鮮度を評価する。ISRを採用する場合も、書込後の失効失敗やプロセス停止で古い公開情報が残るリスクに対処するまで本番適用しない。

## 実装と検証の境界

- サーバーAPIはFirebase ID tokenのUIDを文書パスに使い、デザイン本体を型・件数・サイズで検証する。Firestore `updatedAt` のナノ秒精度をrevisionとして確認し、並行更新を409で拒否する。
- Firestoreへの書込後に、公開resolverで本人へ解決される現行URLと旧別名、原形UIDのURLを失効する。失効失敗時はcommit済revision付き503を返し、UIに再保存を促す。
- ローカルFirestore emulatorでは本人の直接write拒否とAdmin書込許可を確認済み。実ブラウザでの認証済み保存・旧タブ案内と本番配信は未検証。
- 旧データの日本語・記号を含むaliasは、現在の失効ヘルパーのASCII制限から外れる。ISR採用時にはresolverと失効対象の契約を合わせる。
